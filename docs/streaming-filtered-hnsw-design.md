# Adaptive filtering with a resumable HNSW walk

Experimental implementation and rollout proposal for Lucene-backed vector search.

A shopper searches by product image with a price range of $20–$200. If 70% of a 50-million-vector catalog falls in that range, a cold pre-filter can enumerate 35 million eligible products before HNSW scores its first vector. A minimum rating or a combination of price and rating can have the same cost. With a different range or a different catalog, the same query shape might match only a few products, making exact scoring the cheapest choice.

The generic ranked stream is an independent deliverable. Its success criteria are the quality of the first results, time to first result and the ability to continue the same search across polls. The pre-filter benchmarks guide when an ordinary vector query should switch to streaming.

The target workload for automatic filter routing is a **single segment around 5 GB where preparing the pre-filter alone takes at least 500 ms**. Use real product embeddings with their associated catalog attributes. Count how often individual materializations reach 500 ms and report per-filter p95 as well. Cases below 500 ms are acceptable and serve as controls. The earlier synthetic measurements are a harness check. The first real-catalog run observed zero 500 ms materializations in 700 trials on two 5.37 GB HNSW segments. Each held only 312,000 products, and vector-format files accounted for 99.83% of the bytes. A second run retained int8 embeddings and fit 1.13 million products per 5 GiB leaf. Its slowest materialization was 29.43 ms across 700 trials. Both densities are controls. Match the slow leaf’s live vector count and filter-field footprint before using any acceptance result to justify streaming. ## Running the opt-in stage

Use `streaming: {}` in an approximate `$vectorSearch` stage to enable the default walk for that request. Omit the entire field to run the existing stage on the same index. For `$search`, put the same object inside the top-level `vectorSearch` operator and use a Search operator for its filter. All five parameters are optional positive integers.

```javascript
db.products.aggregate([{
  $vectorSearch: {
    index: "catalog",
    path: "embedding",
    queryVector: embedding,
    filter: { price: { $gte: 20, $lte: 200 } },
    numCandidates: 500,
    limit: 48,
    streaming: {
      warmupWidth: 64,
      warmupVisits: 1024,
      refillEvery: 8,
      refillExpansions: 8,
      maxCachedNodes: 250000
    }
  }
}])
```

| Parameter | Default | Meaning |
| --- | ---: | --- |
| `warmupWidth` | 64 | Per-leaf HNSW collector width during the initial search. |
| `warmupVisits` | 1,024 | Per-leaf soft visit limit. Lucene may finish a batch across the limit. |
| `refillEvery` | 8 | Global hit deliveries between lookahead turns. Empty ready queues trigger immediate exploration. |
| `refillExpansions` | 8 | Maximum level-zero adjacency lists expanded in a single leaf refill. |
| `maxCachedNodes` | 250,000 | Maximum distinct scored ordinals across one reader cursor. Exceeding the cap fails the request. Size this for the intended depth of a long drain. |

The stage takes the first `numCandidates` admitted hits from the merged stream and feeds them to the usual sorted collection and configured rescoring. An internal Java caller can instead use `RankedVectorCursor.open(searcher, field, vector, filter, options)` in try-with-resources and repeatedly call `poll(maxHits, workUnits)`. Each poll returns hits and an `exhausted` flag. An empty nonterminal batch means more work is available. Polls share traversal state, and an idle cursor performs no work. A later poll can find a higher score. A full drain covers eligible nodes reachable from the seeds. External stage pagination retains the ordinary bounded result contract. [Cursor](../src/main/java/com/xgen/mongot/index/lucene/streaming/RankedVectorCursor.java) · [Stage adapter](../src/main/java/com/xgen/mongot/index/lucene/streaming/StreamingKnnQuery.java)

The implementation supports root HNSW fields using raw float/int8, scalar-quantized float, auto-binary float/int8 and packed-bit vectors. It uses postings, doc values and Boolean membership over sorted candidate IDs. Legacy one-dimensional point-only ranges can intersect an existing BKD tree per batch. This uses batch-sized match storage and can repeatedly scan many points. Missing vector fields, empty ranges, graphless HNSW leaves and cheaply bounded required terms have dedicated paths. Explicit exact requests, embedded or parent aggregation, per-document tracing, unsupported filter shapes and flat-index codecs cannot select this experimental walk. Omit the option to use the existing implementation for those cases. Automatic acceptance-based routing is deferred pending comparable recall and latency measurements. [Candidate checks](../src/main/java/com/xgen/mongot/index/lucene/streaming/CandidateFilter.java) · [Paired benchmark](benchmarks/vector-prefilter/catalog/int8/README.md#streaming-stage-and-prefix-benchmark)

## Open decisions

Before rollout, agree on the tolerable loss of early-prefix recall, score inversions and first-page latency for a named consumer. Also agree whether that consumer needs every reachable hit or every eligible document, including disconnected components. This draft uses reachable eligible hits for a full graph drain. A promise covering every eligible document additionally requires an ordinal scan for unseen vectors. Callers relying on monotone score order or score-based pagination continue to use the sorted top-k API.

## Benchmark sequence

Define acceptance per leaf as `A / N`, where `N` is the number of live vectors on the queried field and `A` is the number that pass the complete filter. Record both counts. At the same acceptance fraction, a leaf with 10 million vectors may spend much longer building the bitmap than one with 100,000. Compute ground truth outside timed runs on the same index snapshot.

Segment capacity depends on indexed bytes per document. Mongot’s base tiered merge policy uses a byte target that defaults to the smaller of the maximum JVM heap and 5 GiB. An enabled vector merge policy adds its own budgets. Flushes, deletes and merge history produce a range of segment sizes even within one index. For scale, 10 million 768-dimensional float32 vectors alone need about 28.6 GiB before graph and filter data. Time filter translation and weight setup separately so work done earlier is visible. In the benchmark harness, stop after obtaining the accepted set to isolate this cost. Also run the complete existing query on an equivalent cache state and record the chosen exact or ANN path, time to first vector score, and end-to-end p50/p95/p99. Use single-leaf timings for attribution and multi-leaf requests to measure user-visible latency, since leaves can execute concurrently. ### 2. Measure the streaming consumer

Exercise the generic stream immediately on the real catalog graphs. For the routing experiment, compare forced streaming on supported leaves with the current path across the acceptance sweep, including expensive materialization cases as they become available. Replay the same queries and vectors on the same segments, with the same cache conditions, `numCandidates`, `limit`, scoring and rescoring. Interleave repeated runs of both paths. ### 3. Locate the crossover

For each workload, compare **full-query p95 for streaming minus full-query p95 for the existing path** across the measured acceptance sizes. Negative values favor streaming. Use repeated runs to estimate uncertainty and add measurements between adjacent sizes where the sign changes or the difference is within run-to-run noise. Require comparable recall and check p99 and memory at representative concurrency before treating a latency win as actionable.

Report the crossover as a measured range for the tested leaf size, predicate cost, candidate count and cache state. Some workloads may show no win or no single crossing. Use the simplest routing rule the measurements support. Then benchmark that rule on held-out queries, including its estimation cost and wrong-route fallbacks. Keep the existing route wherever the advantage is inconclusive.

## Where to branch

Mongot compiles the filter, resolves `numCandidates` and passes it as Lucene's `k` to its float or byte kNN query. In the pinned Lucene fork (`10.4.0-5`), `AbstractKnnVectorQuery.rewrite` handles match-all and match-none cases, intersects the filter with vector-field existence, creates the weight and schedules leaf searches. Inside `getLeafResults`, `AcceptDocs.fromIteratorSupplier(...).cost()` builds or reuses a bitset and computes its cardinality. Lucene selects exact scoring when that count is at most `k`. Larger sets enter the approximate path, which can still fall back to exact. Mongot's float-specific full-scan heuristic runs inside `approximateSearch`, after the bitmap cost has been paid. [Query factory](../src/main/java/com/xgen/mongot/index/lucene/query/VectorSearchQueryFactory.java) · [Float query](../src/main/java/com/xgen/mongot/index/lucene/query/custom/MongotKnnFloatQuery.java) · [Lucene fork pin](../bazel/java/maven_search_query.MODULE.bazel)

The opt-in query branches during Lucene rewrite so the finite consumer can pull one global candidate budget across all segments on a reader. Warm-up uses the searcher’s task executor. The cursor owns all mutable search state, and the rewritten query holds only the selected document IDs and scores. Standard collectors still sort and apply boosts. If the graph is disconnected and reachable hits underfill the candidate pool, the adapter delegates to the existing Lucene rewrite. Normal queries retain the upstream execution path. The fork has no changes to Lucene’s graph searcher. ## Per-leaf routing after benchmarking

Keep the existing pre-checks. Use the crossover experiment to fill in the streaming decision in the last row. A cheap estimate can select an execution strategy. Only an exact filter match can admit a candidate.

| Evidence available before filter materialization | Execution |
| --- | --- |
| Explicit exact query, rewritten match-none or match-all, missing vectors, or a graphless leaf | Use the existing exact, empty, unfiltered, or codec scan path as applicable. |
| A cheap upper bound on matching vectors is at most `k`, or a small set is economical for the existing full-scan heuristic | Use the existing filtered path and its exact scoring of eligible documents. Preserve the float heuristic and its flag. |
| The filter is selective, a reusable accepted set is already cheaply available, the estimate remains inconclusive after bounded planning, or the cursor or predicate is unsupported | Delegate the whole leaf to the existing filtered search, including its exact fallback. |
| The leaf falls within a measured streaming win and supports candidate membership and codec scoring | Open the cursor and test candidates as they arrive. |

Start with statistics already available to the planner. An equality term’s document frequency upper-bounds its eligible vector count for a single-vector field. For a negated term, subtracting document frequency from the live vector count can undercount when there are deletes or sparse vectors. Use conservative bounds or a measured estimate for the entire Boolean expression. A price interval’s width by itself says little about the number of matching products. If the crossover is sensitive to acceptance and metadata is insufficient, evaluate bounded sampling as a separate routing experiment. Sample vector ordinals, discard deleted documents, and test the complete predicate so a price/rating correlation is represented. Compare the additional setup cost and routing accuracy against simply delegating uncertain leaves to the existing search. A production decision must be cheaper than materializing the filter to find its exact cardinality.

## Cursor contract and traversal

Each segment cursor pins its reader, graph and scorer for the query. It has two phases. Both share a sparse cache keyed by vector ordinal. Each entry holds the traversal score and flags for level-zero expansion and result delivery. A passing candidate also needs its final score and leaf-local document ID. Scores belong to nodes relative to the query. The existing graph already stores the edges.

**1. Find a good starting set.** Run a bounded, unfiltered upper-level descent and level-zero best-first search. Use exploration width and a budget on scored ordinals as the controls. A fixed number of hops can cost very different amounts on different parts of the graph. Collect every distinct ordinal scored, including upper levels, losing branches and neighbors rejected by the top-k collector. A segment's highest buffered hit is the best found so far. A selective predicate can leave this initial set empty.

The first implementation to test is the pinned fork's public `HnswGraphSearcher.search(scorer, collector, graph, acceptOrds)` with a bounded `TopKnnCollector`, a recording `RandomVectorScorer` and a private graph iterator. Capture scalar and bulk scores. During warm-up, forward native bulk scoring and store its returned scores. For continuation, score only cache misses. Start with all cached ordinals eligible for level-zero expansion. Re-reading a warm-up adjacency list once is safe and avoids relying on Lucene's internal expansion state. This also handles a warm-up interrupted partway through a neighbor list. Only mark a node expanded when the resumable walker has considered its full level-zero adjacency. Seed from the entry if warm-up was interrupted before it produced a node. A hard cancellation closes the cursor. [Pinned fork](../bazel/java/maven_search_query.MODULE.bazel) · [Lucene graph searcher](https://lucene.apache.org/core/10_4_0/core/org/apache/lucene/util/hnsw/HnswGraphSearcher.html)

**2. Emit and explore.** Index that cache in two priority queues. The exploration queue orders unexpanded ordinals by traversal score. The ready queue orders eligible, undelivered hits by final similarity, then document ID. Apply live-doc and optional predicate checks after translating ordinals to document IDs. If rescoring is enabled, rescore passing candidates before advertising them to the parent. A filter-rejected bridge remains expandable. A delivered hit can still have an unexplored neighborhood. Popping either queue consumes only that role.

Start phase two with the high-scoring cached branches, regardless of discovery order. A refill expands a bounded amount from the exploration queue, scores new neighbors, and inserts each distinct ordinal once. Do some lookahead after a bounded number of emissions even when the ready queue is full. Otherwise a large warm-up pool could be emitted before discovering an excellent adjacent hit. Bound neighbor inspections and predicate/rescore work as well as new vector scores. A dense patch of already-scored neighbors could otherwise consume an entire poll without decrementing its score budget. Save a partial adjacency list or its position and any undelivered score batch before yielding. Keep the best known head, or report pending, exhausted, or interrupted. An empty ready queue with a nonempty frontier is pending. Exhaustion requires both queues and any partial expansion to finish. The drain covers the level-zero components reachable from the seeds. A request memory cap must report interruption if reached. Keep visited state, deferred branches and ready hits for as long as the cursor promises continuation. [Lucene graph API](https://lucene.apache.org/core/10_4_0/core/org/apache/lucene/util/hnsw/HnswGraph.html)

**Verified warm-up edge case.** On the pinned fork we ran the recording scorer on both 1.13-million-product int8 graphs, with the query from ordinal 42 of leaf 0, collector width 32 and no filter. At visit limit 64, leaf 0 evaluated 67 distinct ordinals and returned zero collector hits. At limit 256 it made 256 score evaluations over 253 distinct ordinals and returned 32 hits. Lucene can finish a bulk scoring call across the visit target or stop in the upper levels. Seed both queues from recorded scores after applying their respective admission rules. Preserve the delegate’s bulk return value and copy ordinal/score pairs before Lucene reuses its scratch arrays. Track calls, ordinals evaluated and unique ordinals separately. Treat the collector limit as a soft work target. Reserve room for a whole incoming batch before recording it, and propagate a hard memory limit or cancellation explicitly.

**Codec support.** Resolve the actual per-field reader on each reopened leaf. The native HNSW reader wraps a Lucene reader, while the binary codec used by the int8 fixture directly constructs a final `Lucene99HnswVectorsReader`. That reader exposes the graph but no public random query scorer. A change to the native wrapper alone would leave the first benchmark running on a different path. Implement the smallest supported graph/scorer capability at the codec boundary. For the binary fixture, first try a codec-owned adapter over its exposed quantized values using its existing scorer factory. Otherwise retain a borrowed flat-reader reference at construction and preserve the delegate's sole close ownership and existing reader capabilities. Verify normal and merge readers, old files, missing fields, empty/graphless leaves, exact score parity and independent graph iterators. Require a counter showing the intended codec and streaming route in every forced-path run. ## Returning a ranked stream across segments

A caller that stops after ten results cares whether those ten approximate the best ten in the entire index. Sorting each batch of ten cannot establish that property. Suppose the best buffered hit scores 0.90 and the next graph node to expand scores 0.80. Expanding it can reveal a hit scoring 0.99. The frontier orders discovered nodes and gives no upper bound on the score behind that 0.80 node. A heap shared by every segment still faces the same unknown. Quantized traversal introduces a second source of reordering when a candidate receives its final score.

**Proposed contract for the generic cursor.** Allow occasional score increases across successive hits. Emit each eligible discovery once if the caller drains a reachable graph to exhaustion. Each emitted prefix should approximate the global top results for that prefix length, ordered by the similarity score the caller sees. Measure the quality of that approximation before choosing search budgets. A caller that requires strictly descending scores needs a different contract. For a fixed candidate pool we can finish retrieval, rescore, sort and page it. For an open-ended monotone stream that emits early, skipping a late, better hit preserves order at a cost in recall and drain coverage. For exact order and complete coverage, the first emission needs either certified bounds on all unseen eligible vectors or sufficient scoring to rule them out. The existing HNSW frontier supplies no such certificate. Pgvector's iterative scans illustrate the choice between strict and relaxed order. [Iterative scan contracts](https://github.com/pgvector/pgvector#iterative-index-scans)

**Merge one advertised head per segment.** Warm participating segments with bounded parallelism on one snapshot. Each gets an initial work slice before the first emission. Exact-search leaves may supply already sorted hits. Keep one entry per ready segment in a parent max-heap, ordered by its best buffered final score and reader-global Lucene document ID for this single-reader cursor. Poll the winner. It can emit successive buffered hits while its next hit outranks the runner-up, up to a bounded burst. Reinsert its refreshed head and choose again. With one ready segment, the burst and work budget still apply. For example, given A at 0.96 and 0.91, and B at 0.94, the parent emits A's 0.96, then B's 0.94 before A's 0.91 if those heads remain current.

A quiet segment can hide a good branch behind a mediocre head. Give pending cursors and nonwinning active cursors bounded refill turns in round-robin order after a fixed total number of emissions. If every cursor is pending, use refill turns to make progress immediately. Refresh a segment's heap entry before the next selection whenever exploration changes its head. Return work-remaining if the poll exhausts its budget. The runner-up score controls emission among known hits. The traversal score belongs to a possibly different scorer, and even the best unexplored node's score gives no upper bound on its neighbors. Use a deterministic schedule counted in expansions and emissions, independent of client page size.

### Ownership, batching and fallback

Expose `open`, `poll(requestedHits, workBudget)` and idempotent `close` internally. A poll returns any committed hits plus a status for remaining work, exhaustion or a hard interruption. A positive budget must advance a frontier, deliver a hit or reach a terminal state. An empty slice can report more work. Serialize polls per cursor. Stage parallel refills privately, then publish ready heads at deterministic scheduling boundaries. An initial barrier gives every leaf its promised slice before the first emission. A leaf can still be pending after that barrier. For one scheduling interval the parent compares only the heads already published. Pin each advertised head during selection or invalidate it by generation before a refreshed head participates. Benchmark this first-hit cost at high fan-out. Tie breaking, refill cadence and burst boundaries must yield the same logical sequence for different page sizes on an uninterrupted snapshot.

The single-reader vector entry point currently materializes a list inside a searcher-reference scope. The manager marks the first search exhausted and the batch producer pages the list. The multipartition reader uses a sorted merge of already materialized partition results and compares tied scores by BSON ID. A late higher score would violate that merge's input contract. Keep the first generic API scoped to one reader. Before exposing it through query/getMore, transfer the searcher reference to a cursor-owning producer, project IDs and stored fields on the pinned snapshot, and provide a coordinator spanning every participating partition with a consistent external tie rule. A Lucene doc ID is unique only inside its reader snapshot. Do not implement relaxed continuation with a last-score or search-after token. [Vector reader](../src/main/java/com/xgen/mongot/index/lucene/LuceneVectorIndexReader.java) · [Vector batch producer](../src/main/java/com/xgen/mongot/index/lucene/LuceneVectorSearchBatchProducer.java) · [Partition merge](../src/main/java/com/xgen/mongot/index/lucene/MultiLuceneVectorIndexReader.java) · [External comparator](../src/main/java/com/xgen/mongot/index/VectorSearchResult.java)

Retain a polled hit until the adapter has accepted it into the output batch. A BSON byte limit can defer even a ready hit to the next batch. Distinguish this from a document too large to return at all. On open failure release previously opened leaves. On kill, timeout, expiry, close racing a refill or reader shutdown, stop scheduling, signal cancellation and wait for outstanding tasks to finish before releasing the searcher exactly once. Charge visited state, both queues, staged predicate/rescore batches and native scratch to a request budget, including parallel reservations. Record pinned-reader lifetime and peak memory across idle and active cursors. [Searcher reference lifecycle](../src/main/java/com/xgen/mongot/index/lucene/LuceneIndexSearcherReference.java)

A finite top-k query can abandon provisional work and retry a leaf before publishing results. An open-ended cursor must choose a drain-capable implementation for every participating leaf up front. For a small exact leaf, enumerate and sort all eligible hits. A large unsupported leaf needs an explicit unsupported outcome or a separately budgeted exact provider. After publication, keep the original snapshot and delivered set. An unhandled hard limit or failure ends the cursor with an explicit reason. Restarting through ordinary top-k would lose the tail or repeat already returned hits.

### Where Lucene radial search fits

The pinned fork exposes `FloatVectorSimilarityQuery` and `ByteVectorSimilarityQuery`. They separate a result similarity cutoff from a lower or equal traversal cutoff, allowing weaker nodes to lead to a qualifying neighbor. The built-in collector is package-private. Its approximate path accumulates threshold hits and the query sorts them by document ID for its scorer. The public query exposes completed matches. A subsequent wider query starts a new search. The filtered query path also calls `AcceptDocs.cost()` in the pinned fork. [Similarity query API](https://lucene.apache.org/core/10_4_0/core/org/apache/lucene/search/FloatVectorSimilarityQuery.html) · [Similarity query implementation](https://github.com/apache/lucene/blob/releases/lucene/10.4.0/lucene/core/src/java/org/apache/lucene/search/AbstractVectorSimilarityQuery.java) · [Threshold collector](https://github.com/apache/lucene/blob/releases/lucene/10.4.0/lucene/core/src/java/org/apache/lucene/search/VectorSimilarityCollector.java)

Use stock radial search as a fixed-threshold baseline. For the stream, reuse the two-cutoff idea if experimenting with score-guided refills. The parent supplies a final-score cutoff for a burst. The leaf may separately use a traversal-score floor to prioritize expansion. Park lower-scoring branches for later polls and relax the traversal floor when needed. Always cap the work per slice. Begin with best-first, budgeted refills as the simpler baseline. Add a traversal floor only if it improves prefix quality or reduces work at matched latency.

A one-query check on the existing 1.13-million-product int8 leaves illustrates threshold sensitivity. We used the vector at ordinal 42 of the first leaf and set each leaf's result threshold to the traversal similarity of hit 64 in its ordinary unfiltered byte kNN query. On leaf 0, keeping both thresholds equal gave one hit in 76 visits. Lowering only the traversal floor by 0.005 produced 1,380 hits in 667,564 visits. On leaf 1 the same floor adjustment produced zero hits in 205 visits. These are codec scores and collector visit counts on this fixture. They establish neither a default score margin nor a recall estimate.

## Testing the filter during collection

Give the filtered consumer one leaf-local operation that evaluates the compiled filter for a batch of candidate document IDs and returns a match mask over those positions. The cursor has no filter-specific branches. Sort candidate positions by leaf doc ID for forward-only iterators, then map the mask back to exploration order before collection. Obtain fresh iterators when a later batch moves backwards. Memory for predicate results scales with batch size.

| Filter | Candidate test using the existing index |
| --- | --- |
| Numeric range or threshold, e.g. price between $20 and $200 or rating ≥ 4 | Use the doc-values alternative of each compiled numeric range branch. For ascending candidate IDs, use its approximation and two-phase confirmation where supplied, or the equivalent encoded bounds on numeric doc values. Preserve the factory’s integer/double branches and inclusive/exclusive endpoints. A missing numeric value fails that branch. |
| Equality or exclusion, e.g. brand equals A or item differs from X | Seek the compiled term and advance its postings across the batch. Use the resulting mask for equality. For exclusion, subtract it from the applicable positive scope. |
| Compound filter, e.g. price in range **and** rating ≥ 4 | Combine the child masks for the same candidate batch. Apply the compiled Boolean requirements, including any minimum number of matching clauses. A short-circuited candidate needs no further tests once its result is known. |

Derive the evaluator from the existing translated query so the range endpoints, field names and array semantics come from one place. Capability is per leaf and applies to the entire expression. Legacy scalar numeric fields have a doc-values range alternative. Legacy multi-valued numeric branches can be points-only. An absent branch contributes no matches. The forced-path experiment uses per-batch BKD intersection for a populated points-only range. A future automatic planner should price that operation separately from doc-values membership. Preserve the factory’s distinction between a fused interval and two comparisons that may match different elements of an array. The same whole-filter fallback applies to unhandled wrappers or embedded scopes. Creating a generic scorer that enumerates a dense range would defeat the optimization. The bounded adapter returns candidates in traversal-score space and leaves both existing rerank stages in place. An alternative stopping policy for a future finite query would keep a leaf-local top-k heap of passing candidates and count all vector scoring work, including rejected candidates and upper-level visits. Use Lucene’s score and document-ID tie order so results can enter the existing merge. Use the resolved `numCandidates` for the ANN pool. A full pool alone is a poor stopping condition because early neighbors near the entry can be mediocre. As an initial policy, finish the current expansion and stop when the pool is full and the best pending score is below the competitive score, with deterministic tie handling. This is an approximate HNSW stopping rule. Benchmark recall against exact filtered results before enabling it. The separate generic cursor retains the frontier after this heuristic would have stopped a finite query.

For a future automatically routed query, if observed acceptance is poor or the walk approaches its visit or memory allowance, close it and run the existing filtered route once on the same leaf. Discard the local heap before calling the superclass. For the existing top-k API, its collector manager can then use the normal cross-leaf thresholds without having seen any provisional hits. Successful streaming leaves contribute sorted results to the same final merge. Include the cost of forgoing cross-leaf pruning in the benchmark. On reachable exhaustion with fewer than `k` hits, use the existing exact completion behavior to cover any unreachable qualifying vectors. On cancellation or timeout use the normal query outcome and release the cursor immediately.

## Validation and benchmark gates

### Correctness before performance

Use small, hand-constructed graphs for invariant tests and the real catalog HNSW graphs for performance. Keep two independent oracles. For ranking, enumerate all live vectors on the snapshot, apply the ordinary compiled Lucene filter, score in the final output space and sort with the declared tie rule. For drain coverage, independently traverse the level-zero graph from the same seeds and intersect the reachable set with the oracle's eligible documents. A disconnected eligible document belongs in global rank truth even when the walk cannot reach it.

| Failure to provoke | Check |
| --- | --- |
| Rejected or deleted bridge, sparse ordinal mapping, a high scorer found late | The bridge is expandable, every returned ID maps to the correct eligible document, reachable hits appear exactly once on full drain and the late improvement remains observable. |
| Upper-level-only warm-up, repeated ordinals, reused bulk buffers, partial neighbor batch | Compare recorded scalar and bulk scores to the codec on the same ordinals. Pause after every possible boundary on a tiny graph. The completed sequence and reachable set match the uninterrupted run. |
| Empty leaf, no eligible vectors, ties, fewer than k matches, all matches in a slow leaf | An empty ready heap can remain pending. Exhaustion requires no remaining traversal, pending evaluation or output. A cold losing leaf gets its scheduled turn and equal-score ordering uses the appropriate ID domain. |
| Missing fields, negative predicates, mixed scalar/array or integer/double branches, points-only data | Differentially compare per-document candidate masks to the compiled filter, including backward doc-ID batches. A populated unsupported branch delegates or fails capability negotiation before emission. |
| Full output batch, oversized document, refresh/merge, concurrent close, worker exception during open or refill | Account for every buffered hit, reader and task. Inject faults after partial setup, after selecting a head and after publishing a batch. Check no duplicate delivery across successful polls and no resource leaks. |
| Mixed routes in a finite query, timeout and optimistic re-entry | Verify global ID offsets exactly once, upstream ranking/ties on a fixed candidate set, exact fallback when required, original timeout semantics, and honest metrics for retries. Exercise normal and explain entry points, including codec fallback. |

A cursor passing these checks is ready for a forced-path quality benchmark. Wire exposure additionally requires integration tests through the normal first-batch/getMore/kill path, with document-count and BSON byte limits and a refreshed index between batches. An internal empty work slice needs handling inside the adapter so existing callers cannot interpret it as EOF.

### Implementation order and release decisions

1. **Leaf cursor and codec probe.** Implement the recording warm-up, level-zero continuation, independent traversal/delivery state, cancellation and accounting. Run invariant tests and prove the actual int8 reader uses the opted-in path.
2. **Generic ranked cursor.** Add the deterministic coordinator and per-hit final-score path. Run held-out prefix-quality and latency comparisons, starting with one reader and multiple segments. Agree quality targets with the intended consumer before evaluating held-out results. Expose a generic consumer only for configurations satisfying its ordering, coverage and lifecycle contract.
3. **Finite filtered adapter.** Introduce candidate membership and the `searchLeaf` adapter behind an opt-in. Compare the forced paths before enabling any estimator. Test rare exact sets, ordinary selective filters and broad filters with zero accepted-set materializations on supported leaves. Retain existing exact/bitmap routing for unsupported configurations.
4. **Adaptive rollout.** Enable only measured regions with an end-to-end advantage and acceptable recall, CPU and memory at representative concurrency. Track chosen route, estimated match fraction, observed candidate pass fraction, warm-up overshoot, fallback reason and total work. Test disabling the feature and replay the same pinned fixtures when upgrading mongot or Lucene. Keep the ranked cursor's enablement independent of the adaptive filter decision.
